## **Purpose**

SimpliFoundation is SimpliCreative’s human-led custom implementation engagement.

Its purpose is to translate approved strategy into a working digital foundation without losing the strategic reasoning, evidence, priorities, requirements, or client decisions established upstream.

Foundation is primarily executed by humans.

AI supports the work through governed retrieval, research, data synthesis, first-draft generation, comparison, validation support, decision capture, and knowledge preservation.

AI does not own Foundation strategy, design, development, technical architecture, client communication, or final implementation decisions.

The governing principle is:

`STRATEGY_MUST_SURVIVE_EXECUTION`

The engineering objective is to give human specialists the right approved context at the right time, reduce unnecessary reconstruction of client knowledge, support intelligence-heavy work, and preserve meaningful decisions without turning every project activity into permanent knowledge.

## **Foundation Entry Paths**

SimpliFoundation may begin through either approved path:

`APPROVED SIMPLIBLUEPRINT → FOUNDATION`

or

`DIRECT-TO-FOUNDATION SCOPING → FOUNDATION`

The Intelligence Layer must know which entry path applies.

When Foundation follows SimpliBlueprint, the approved Blueprint becomes the primary client-specific strategic source for implementation.

The Foundation handoff should include approved findings, recommendations, implementation requirements, priorities, measurement requirements, client decisions, relevant evidence relationships, constraints, dependencies, and unresolved implementation questions.

When Foundation follows Direct-to-Foundation Scoping, the approved Foundation Scoping Record and validated existing client strategy become the primary implementation sources.

Foundation should not recreate strategy merely because implementation has begun.

If material strategic uncertainty emerges during implementation, it must be surfaced for human strategic review.

## **Strategic vs. Implementation Unknowns**

Foundation must distinguish normal implementation discovery from material strategic uncertainty.

| Unknown Type | Definition | Route |
| ----- | ----- | ----- |
| Implementation Detail | Determines how an approved strategic requirement should be executed | Human implementation decision |
| Material Strategic Unknown | Could change what should be built, why, for whom, priority, or success definition | Strategic review required |

AI may classify and flag.

AI may not independently resolve Material Strategic Unknowns.

When one emerges, return:

`MATERIAL_STRATEGIC_UNKNOWN_REQUIRES_HUMAN_REVIEW`

Foundation should not quietly absorb new strategic work into implementation.

## **AI Draft State Model**

AI-generated content is never automatically authoritative.

Use:

`AI_GENERATED → HUMAN_REVIEWED → CLIENT_REVIEWED when required → APPROVED → SEMANTIC_MEMORY_ELIGIBLE`

| Status | Meaning |
| ----- | ----- |
| Draft | Working material |
| Human Reviewed | Human has evaluated it |
| Client Review | Awaiting client decision |
| Approved | Authorized for use or implementation |
| Superseded | Replaced by a newer approved version |
| Historical | Retained for reference |
| Rejected | Deliberately not approved |

Retrieval should prefer the current approved record.

## **Change Classification**

| Change Type | Definition | Route |
| ----- | ----- | ----- |
| Clarification | Resolves detail without material scope or strategy impact | Human implementation |
| Implementation Decision | Determines how an approved requirement is executed | Human implementation decision |
| Scope Addition | Adds responsibility, deliverable, or material effort | Commercial review |
| Strategic Change | Changes what, why, who, priority, or success definition | Strategic review |

AI may detect possible changes.

It may not approve Scope Additions or Strategic Changes.

`project_management_system = monday.com`

`design_system = Figma`

## **Knowledge Capture Filter**

Before writing routine project activity into persistent memory, ask:

| Question | If No |
| ----- | ----- |
| Does this change an approved client fact? | Do not persist as durable knowledge |
| Is this a material decision? | Do not create Decision Record |
| Does this change strategy or requirements? | Treat as routine activity |
| Does this create a durable client preference? | Treat as routine activity |
| Does this affect scope, risk, or commitment? | Treat as routine activity |
| Will this provide useful future context? | Do not persist |
| Is this meaningful evidence or an outcome? | Do not persist |

The governing rule is:

`USEFUL_INTELLIGENCE != COMPLETE_ACTIVITY_LOG`

## **Gold-Standard and Reference Use**

Gold-Standard examples may calibrate structure, depth, reasoning, and quality.

Reference examples may help specialists recognize useful application patterns.

Neither creates client-specific truth.

The governing rules are:

`EXAMPLE = APPLICATION_REFERENCE`

`EXAMPLE != POLICY`

`EXAMPLE != CLIENT_EVIDENCE`

`REFERENCE_EXAMPLE_DOES_NOT_AUTHORIZE_REUSE`

A previous client’s messaging, architecture, CMS recommendation, integrations, design decisions, copy, scope, pricing, or implementation requirements should not be transferred to another client without independent supporting context.

## **Strategic Fidelity QA**

Before launch, compare:

`Approved Strategy ↔ Implemented Experience`

`Approved Messaging ↔ Final Content`

`Blueprint Recommendations ↔ Implementation`

`Page Requirements ↔ Final Pages`

`Conversion Requirements ↔ Implemented Conversion Paths`

`Measurement Requirements ↔ Implemented Tracking`

`Discoverability Requirements ↔ Implemented SEO / AEO / GEO`

`Approved Claims ↔ Published Claims`

`Client Decisions ↔ Final Implementation`

Material discrepancies should be flagged for review.

Do not silently rewrite an approved requirement to match what was implemented.

## **Launch**

Production launch is human-controlled.

AI may prepare launch checklists, summarize unresolved issues, compare implementation against requirements, prepare measurement documentation, identify missing approvals, and flag unresolved strategic or technical risk.

AI may not authorize or independently execute production launch.

The Launch Record should preserve the approved launch state and any known accepted limitations.

## **Post-Launch Intelligence**

## **Engineering North Star**

The Foundation Intelligence Layer should not attempt to automate SimpliCreative’s specialists.

It should make specialists better informed, reduce the context they have to reconstruct manually, preserve the strategy established upstream, and make meaningful human judgment durable.

The system should reliably answer:

What has already been approved?

What strategy governs this work?

Which Blueprint recommendation or Foundation requirement does this work fulfill?

What evidence supports that requirement?

What are we trying to accomplish?

What does this client prefer?

What changed?

Why did we make this decision?

What remains uncertain?

What should not be inferred?

Has implementation drifted from approved strategy?

What happened after implementation?

What is worth remembering?

The desired outcome is not autonomous Foundation delivery.

The desired outcome is human specialists working from better context, with AI handling retrieval, synthesis, structured first drafts, comparison, and intelligence preservation where those capabilities genuinely improve the work.
